---
title: Choose the right test boundary
description: Decide when a mock, fake, HTTP stub, local emulator, real service, or provider sandbox gives the evidence a test needs.
---

localhost2137 is not the right default for every test. The useful question is not “How realistic can
this test be?” but “What is the smallest boundary that could expose the defect this test cares
about?”

A pure calculation usually needs no service process. A provider integration may need to prove SDK
serialization, state transitions, callbacks, or time-derived work. A focused double can model some
of those claims; others require the protocol or service boundary the double leaves out.

## An evidence ladder, not a quality ladder

Each approach is strong at a different claim:

| Boundary | Useful evidence | What it does not establish |
| --- | --- | --- |
| Interaction mock | Your code chooses the expected branch and calls a dependency with expected values. | Behavior behind the call, coherent provider state, or transport behavior. |
| In-process fake | Your code works against simplified behavior, including coherent state and transitions when the fake models them. | Provider SDK serialization, HTTP or callback transport, or behavior the fake omits. |
| HTTP stub or recorded response | The application sends a particular request and handles a known response. | Coherent state across calls or provider-initiated work unless every transition is scripted. |
| localhost2137 plugin | The application speaks a documented provider-shaped API against a local world with isolated plugin state. | Provider behavior outside the plugin's explicit compatibility surface or real production infrastructure. |
| Real service in a local container | The application interoperates with that runnable service build. | Hosted-only provider behavior, managed configuration, or features absent from the selected build. |
| Provider sandbox or test mode | The application reaches provider-owned behavior and account configuration. | Offline determinism or exact production equivalence. Isolation, cost, and privileged state controls vary by provider. |

The rows are not successive levels of engineering maturity. Replacing every unit mock with a local
service makes a suite slower and harder to understand without improving a pure logic claim. Replacing
every provider check with an interaction mock makes the suite fast while leaving the real integration
boundary untested.

## Where a stateful emulator earns its cost

A localhost2137 test becomes a candidate only when a smaller boundary cannot expose the relevant
failure. Signals include:

- the relevant SDK or HTTP mistake depends on coherent state created by earlier requests;
- a local actor or clock change should cause an event, callback, or webhook;
- the test needs to arrange or inspect state that a production API should not expose;
- several tests need independent service worlds without separate provider accounts.

These are signals, not checkboxes. An in-process fake can model coherent state, and an HTTP stub can
inspect a request. If either can falsify the claim without bypassing the behavior under test, prefer
that smaller boundary.

The installed plugin must still implement the behavior. A stateful runtime cannot turn a missing
endpoint, event type, retry rule, or SDK encoding into a valid compatibility claim. Inspect the
plugin's supported surface before choosing the test boundary.

## Keep the application path real

The emulator adds a privileged control interface alongside the provider-shaped interface. That
split is useful only when the test keeps their jobs distinct:

```text
operation ── arrange or trigger ──> local service state
application ── SDK or HTTP ───────> the same local service state
operation ── inspect ─────────────> the resulting local service state
```

If a test creates a subscription through an operation while claiming to verify that the application
can create one through its provider SDK, the test has skipped its own subject. If the claim is about
how the application reacts to an existing subscription, arranging that prerequisite through an
operation is appropriate.

The claim, not a blanket rule, decides the route. [Operations and emulated APIs](/operations-and-apis)
works through this distinction for outgoing requests, inbound callbacks, and time-derived behavior.

## What a local emulator cannot prove

Even a well-tested plugin is a compatibility subset. A local test does not establish:

- behavior the plugin does not document and exercise;
- real account permissions, provider configuration, DNS, TLS, or internet routing;
- production rate limits, regional behavior, scale, latency, or availability;
- compatibility with an SDK version the plugin has not tested;
- that secrets, webhooks, or dashboards are configured correctly in an external account.

Those are reasons to retain a small provider-facing contract or end-to-end suite where the risk
justifies its cost. They are not reasons to move every application scenario into an external
sandbox.

## Layer boundaries around the defect

Depending on its risks, a suite may combine these scopes:

1. Function-level tests cover business rules and edge cases without a service runtime.
2. Focused localhost2137 tests can cover the provider protocol, state transitions, callbacks, and
   controllable time that the installed plugin actually supports.
3. A smaller provider-facing suite checks external credentials, account configuration, and a few
   critical compatibility paths.

Not every integration needs all three. Keep an individual behavior at the lowest layer that can
falsify it. Duplicate a scenario at another layer only when the second boundary answers a different
question.

For example, a unit test can prove which invoice state should suspend an account. A local emulator
test can prove that the application reads a provider-shaped invoice through its SDK and applies that
rule after a renewal callback. A provider sandbox check can prove that the deployed credentials and
webhook configuration receive the external event. These are related tests, not three increasingly
impressive versions of the same test.

## When to stop before adding localhost2137

Do not add a plugin merely because the application imports an external SDK. Stop when:

- the behavior under test is completely inside your own code;
- an HTTP stub already exposes the only request or response mistake that matters;
- the required provider behavior is outside the plugin's supported surface;
- a real, lightweight local service already supplies the exact implementation you need;
- the goal is load, security, resilience, or production-network testing.

When a plugin does fit, start with its documented compatibility boundary, not its package name or a
promise of general provider parity. [Using plugins](/plugins/using) gives the evaluation checklist.
Then use [Getting started](/getting-started) for a complete local loop or
[Run an existing application](/existing-application) to connect an existing project.
