---
title: Callbacks and webhooks
description: Understand how provider-shaped events travel from a plugin to an application, what delivery guarantees belong to plugins, and what idle waits establish.
---

Pointing an SDK at a local API covers only one direction of an integration. Providers also initiate
requests: event callbacks, webhooks, delivery receipts, and similar notifications enter the
application without an application request immediately preceding them.

localhost2137 does not turn those requests into function calls. A plugin that supports callbacks
sends a provider-shaped HTTP request to the application's configured receiver. For that supported
surface, the application can keep its normal routing, body parsing, signature validation, and
handler code.

## One scenario crosses both directions

Consider a bot that replies to a message:

```text
test or agent ── trigger operation ──> plugin state
                                           │
                                           └── signed event ──> application handler
                                                                    │
plugin API <──────────── provider SDK request ───────────────────────┘
```

The trigger operation represents an actor outside the application. The callback then exercises the
application's inbound provider boundary, while the SDK request exercises its outbound provider
boundary. All three interactions act on one plugin-owned world, but they are not interchangeable.

Calling the handler directly would test application logic without HTTP parsing or signature
validation. Writing the reply through another operation would skip the application's SDK request.
Either can be correct for a narrower claim; neither proves the complete loop shown above.

[Operations and emulated APIs](/operations-and-apis) develops this distinction for arrangement,
triggers, application traffic, and observation.

## The plugin chooses how to configure the receiver

The runtime does not define a universal callback destination or environment variable. Each plugin
chooses how its receiver is configured. The first-party Slack plugin uses an `eventsUrl` config
field; the Stripe plugin uses `webhookUrl`. Both default to `null`, so installing either plugin does
not send callbacks until its receiver is configured.

For a destination defined in plugin config, the value belongs to the runtime template rather than an
instance. Creating another instance therefore creates independent plugin state but not another
callback URL. The runtime does not add an instance header, rewrite the configured destination, or
teach a shared receiver how to correlate events; a plugin may supply provider-shaped correlation
data as part of its documented event.

This is separate from an instance's connection values. The application receives a provider-shaped
API URL and local credentials for requests it initiates. The plugin receives the callback URL and
signing configuration it needs for requests it initiates. The runtime control token belongs to
neither application path.

The receiver must be listening before a scenario triggers delivery. Changing a config-based
destination requires a runtime restart because the current runtime loads configuration once; it is
not hot reloaded.

## The plugin owns delivery semantics

The runtime supplies tracked outbound fetch and a task tracker. It does not define a universal event
envelope or delivery policy. Each plugin owns:

- which state transitions create an event;
- the request body, headers, signature, event identity, and timestamp;
- which response counts as success;
- timeout and retry behavior;
- persistence, recovery, ordering, and duplicate-delivery rules;
- the operations that expose enough control and inspection to test those rules.

Those details are part of the plugin's compatibility surface. One plugin may document no retries;
another may provide bounded retries or at-least-once delivery. localhost2137 itself does not promise
exactly-once delivery, and a test should not infer it from `idle()`.

The two first-party plugins illustrate the difference. Slack sends signed Events API bodies and
persists bounded attempts whose later deadlines are driven by positive clock advancement. Stripe
commits invoice events and webhook outbox rows together; after an interrupted delivery, recovery may
send the same stable event ID and body again. These are plugin guarantees backed by their own tests,
not behavior the runtime silently applies to every plugin.

## What `idle()` establishes

`await instance.idle()` waits until the instance has no registered plugin work after a microtask
turn. It includes nested work registered by work that is completing, and it surfaces a tracked
failure instead of turning that failure into a timeout or arbitrary sleep.

Its scope matters:

| Question | Does `idle()` answer it? |
| --- | --- |
| Did the plugin's currently tracked delivery attempt settle? | Yes. |
| Did nested work registered by that attempt settle? | Yes. |
| Did a retry scheduled for a later virtual instant run? | No; advance time according to the plugin's documented policy. |
| Did the application finish unrelated background jobs after returning its HTTP response? | No; the application needs its own completion boundary. |
| Will a provider or external network behave the same way? | No. |

An HTTP response can acknowledge a callback before the application finishes all resulting work.
After `idle()` establishes plugin-side settlement, wait on the application's public effect, queue,
or test hook when the claim includes that later work. Do not make one broad sleep stand in for both
sides.

[Virtual time and asynchronous work](/virtual-time) defines pinned and real clocks, durable
advancement, tracked tasks, and later retry deadlines.

## Delivery may be repeated

Applications consuming a documented at-least-once event stream should normally treat event identity
as the deduplication boundary: a sender can lose confirmation after the receiver has already
committed its effect. A local plugin can reproduce that condition only if its documented delivery
model includes stable event identity and redelivery.

A repeated request is useful evidence when the test claims that the application applies one effect
for one event. It is noise when the plugin invents duplicates the provider does not produce. Inspect
the plugin's event and retry contract before writing the scenario; the runtime cannot decide the
provider rule on its behalf.

## Parallel receivers require a routing rule

Separate instance storage never proves callback routing. Some plugins define one callback
destination in mount config. When an installed plugin does, every instance of that mount uses the
same configured destination even though its service state remains isolated. Other plugins may define
different destination or correlation behavior; inspect the installed plugin contract before running
parallel deliveries.

When several instances deliver to one receiver, database, or queue, parallel tests need one of three
deliberate designs:

- correlate callbacks using provider-shaped event data the plugin actually supplies;
- serialize scenarios that cannot be correlated safely;
- run separately configured runtimes and receivers.

Do not rely on an undocumented instance header or URL rewrite. Do not pass the runtime control token
to the receiver as a workaround. [Instances and isolation](/instances#where-the-boundary-stops)
explains why configuration is outside instance state, and
[Integration testing](/testing#share-one-runtime-across-worker-processes) shows the worker ownership
model.

## Read the result narrowly

A successful local callback test can establish that the installed plugin produced its documented
request, the application accepted it through its normal HTTP handler, and the observed application
effect followed. If the application then uses its normal SDK against the emulated API, the scenario
can also exercise the response path.

It does not establish external DNS, TLS, dashboard configuration, provider account permissions, or
behavior outside the plugin's support matrix. Keep provider-facing checks for those claims. Read the
installed plugin reference for exact signatures, retry rules, and deliberate differences before
treating a local event as evidence of provider compatibility.
