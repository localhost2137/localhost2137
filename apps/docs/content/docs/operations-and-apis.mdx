---
title: Operations and emulated APIs
description: How to choose the boundary that arranges, triggers, exercises, and observes a local service world.
---

Every emulator plugin has two interfaces over the same local state.

- The emulated API is the provider-shaped boundary used by the application.
- Operations are privileged controls used by tests, scripts, developers, and coding agents.

Neither interface is more real than the other. They have different jobs. A useful test chooses
between them according to the claim it needs to prove.

```text
application ── SDK / HTTP / callback ──> emulated API
                                                │
test or agent ── operation / CLI / control HTTP ─┘
                         one service world
```

## Start with the claim

Suppose a test claims that a bot receives a Slack message and replies through Slack's Web API. That
claim crosses two application boundaries: the signed callback entering the bot and the SDK request
leaving it. Calling a `sendMessage` operation can trigger the callback, but it cannot stand in for
the bot's outbound SDK request.

A different test might claim only that a plugin creates one message and persists it. An operation
can be the interface under test in that case. The boundary follows the claim, not a rule that
operations are suitable only for setup.

| Role in a scenario | Usually appropriate boundary |
| --- | --- |
| Arrange users, catalog entries, accounts, or other world state | Operation |
| Trigger an external actor, callback, failure, or clock event | Operation or runtime capability |
| Exercise application integration with a provider | The application's normal SDK, HTTP client, or callback handler |
| Observe emulator state | Inspection operation or supported provider API |
| Observe application behavior | The application's public output or effect |

Operations are valid for arranging, triggering, and observing. They weaken the evidence only when
they replace the application-facing interaction named by the claim.

## One Slack scenario, several boundaries

The repository's Slack Bolt example uses operations to construct and act on a local workspace:

```ts
const ada = await instance.slack.createUser({ name: "Ada" });
const channel = await instance.slack.createChannel({ name: "general" });
await instance.slack.addUserToChannel({ channel: channel.id, user: ada.id });

await instance.slack.sendMessage({
  channel: channel.id,
  from: ada.id,
  text: "ping",
});
await instance.idle();

const messages = await instance.slack.listMessages({ channel: channel.id });
expect(messages.map(({ text }) => text)).toEqual(["pong", "ping"]);
```

Each call has a distinct role:

1. `createUser`, `createChannel`, and `addUserToChannel` arrange the world.
2. `sendMessage` represents an external user and triggers a signed Events API callback.
3. The Bolt application receives that callback through its normal handler.
4. The application calls `chat.postMessage` through Bolt's normal Web API client.
5. `listMessages` observes the shared workspace after tracked work becomes idle.

The trigger is an operation because the external user is outside the application under test. The
inbound callback and outbound Web API request use Slack-shaped interfaces because those are the bot
integrations the example claims to exercise.

Replacing the bot's `chat.postMessage` call with a message-writing operation could still produce
`pong`. It would no longer prove that the application can post through its Slack client.

## Operations control what provider APIs should not

Provider APIs are designed for provider customers. They often cannot create the surrounding world
a local test needs: an arbitrary user, a payment outcome, a delivery failure, or the passage of 30
days. Adding fake provider endpoints for those actions would make the emulated API less compatible
and couple test setup to invented application-facing behavior.

Operations expose that control explicitly. Their Zod schemas also let the runtime validate the same
call through a typed instance handle, generated CLI, or control HTTP. The plugin still owns the
meaning of the operation; the runtime only supplies the adapters and execution boundary.

An operation succeeding says nothing by itself about provider compatibility. That requires tests
through the provider-shaped route, request encoding, callback, or target SDK. Conversely, an SDK
request says little about whether the plugin offers enough control to arrange useful worlds. A
plugin needs evidence for both interfaces.

## The Stripe boundary moves with the claim

The Stripe SDK example arranges a product and price through operations, then creates a customer and
subscription through the official SDK. After the instance clock advances by 30 days, it lists
invoices through the SDK.

That final SDK read matters because the example claims the application's Stripe client can observe
the renewal. If the claim were instead about the plugin's durable renewal rule, an operation could
inspect invoices without weakening it. Kernel and plugin tests can then concentrate on committed
clock movement, idempotent reconciliation, and recovery rather than SDK behavior.

The same action can therefore be a valid observation in one test and the wrong boundary in another.
State does not determine the evidence; the claim does.

## A plugin has one domain, not two implementations

Sharing state is not enough if routes and operations implement separate business rules. A plugin
should keep provider routes and control operations as adapters over the same domain behavior:

```text
provider route ─┐
                ├── domain behavior ── plugin persistence
operation ──────┘
```

This keeps provider response mapping out of operations and CLI concerns out of service logic. It
also lets tests compare both interfaces against the same resulting state. Plugin-specific rules,
including retries and errors, remain inside the plugin rather than leaking into the runtime.

The separation has a cost: a plugin author must design both an honest compatibility surface and a
useful control surface. A broad operation inventory can also make weak tests easy to write when the
claim is left implicit. Naming the claim and its application boundary is the guardrail.
