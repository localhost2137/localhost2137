---
title: Diagnose a failing scenario
description: Locate a failure across project discovery, the runtime, a provider-shaped API, callbacks, and application completion without hiding the broken boundary.
---

Diagnosis is successful when you know which boundary failed. It is not successful merely because a
test passes after adding a sleep, replacing an SDK call with an operation, or clearing all local
state.

Start with one failing scenario. Record its instance ID, service key, config path, command or
application request, and expected application effect. Keep those identifiers fixed while you move
through the checks below.

## Check the project before the scenario

Run the read-only project inspection first:

```sh
pnpm exec localhost doctor --json
```

`doctor` loads the resolved config, inspects runtime discovery, and reads stored manifests. It does
not start a daemon, create directories, or repair state. Check these parts of its result:

- `config.loaded`, `config.path`, and `config.storageRoot` identify the project that was inspected;
- `runtime.state` distinguishes an absent runtime from an unhealthy or healthy one;
- `issues` reports config, discovery, manifest, service-version, and pending-cleanup problems;
- `storage.instances` reports each stored world's status, seed status, and service keys.

An absent runtime is expected before `localhost dev` starts. A config fingerprint mismatch means the
running daemon still has a different resolved config; restart it after saving the intended config.
Fix config import and discovery failures before interpreting plugin behavior.

Do not delete `.localhost2137` to silence one issue. Reset or destroy an explicitly named instance
when that is the intended recovery. Preserve an unexpected manifest or pending trash entry until you
have recorded the diagnostic.

Config import errors report one of two boundaries. `CONFIG_DEFAULT_EXPORT_MISSING` means the selected
module loaded but did not default-export a config. `CONFIG_IMPORT_FAILED` means evaluating that module
or one of its imports threw; inspect the original process output and the selected path rather than
changing module format speculatively. TypeScript, ESM, CommonJS, and local imports are supported.

## Recover a storage lock safely

One daemon owns a storage root. `LOCKED` names a process that is still alive; use that daemon, stop it
normally, or choose another storage root. Do not remove its lock.

`LOCK_STALE` names a stopped owner. `LOCK_CORRUPT` means the lock has incomplete or invalid owner
metadata. Both errors print the exact lock path. First confirm no runtime uses that storage root,
including another terminal or test process. Then remove that exact lock path and retry. Never turn
the printed path into a wildcard or replace it with the project directory.

If another runtime may be starting, retry before treating a damaged-looking lock as abandoned.

## Confirm the selected world

Ask the running daemon what it actually exposes:

```sh
localhost_service_key="replace-with-configured-service-key"
localhost_instance_id="replace-with-instance-id"
pnpm exec localhost describe "$localhost_service_key" --instance "$localhost_instance_id" --json
pnpm exec localhost env --instance "$localhost_instance_id" --format json
```

The service name is the key from `services` in your config, not necessarily the plugin package name.
Use `describe` or generated `exec` help for the installed operation names and inputs. Do not copy an
operation from documentation for a different plugin version and treat its absence as a runtime bug.

When a connection value is a URL, check that it names the same instance and service. `env` contains
application-facing connection values only. The control token is separate and must not enter the
application, browser code, logs, screenshots, or a bug report.

## Classify the first broken boundary

Follow the request from left to right and stop at the first place where observed behavior differs
from the claim:

| Symptom | Boundary to inspect first | What it establishes |
| --- | --- | --- |
| Config will not load, or the wrong project is found | Config resolution | The intended plugin set has not reached a runtime yet. |
| `describe`, `exec`, or instance commands cannot reach the daemon | Discovery, control authentication, or instance selection | The control path failed before a plugin operation ran. |
| An operation rejects its input or fails | Operation schema or plugin control behavior | Privileged setup or inspection failed; it says nothing by itself about the provider-shaped API. |
| The application SDK or HTTP client receives an unexpected response | Provider-shaped HTTP surface and application adapter | The normal application integration path was exercised. |
| A callback is absent | Callback configuration, receiver, signature handling, or delivery | The outbound delivery path needs to be traced separately from the triggering request. |
| `idle()` rejects | Idle control request and tracked plugin work | Its error distinguishes failed work, timeout, cancellation, or another control failure; an arbitrary delay is not completion evidence. |
| `idle()` succeeds but the expected application effect is absent | Application completion | Plugin-owned work is idle, but the application may still have its own queue, transaction, or background job. |
| Behavior changes after reset or restart | Instance lifecycle or persisted plugin state | The failure depends on world state or reconciliation rather than only the request. |
| The local result differs from the real provider | Documented compatibility surface | The gap may be unsupported behavior; it is not automatically an emulator defect. |

This classification prevents a common false fix: arranging the desired result through an operation
when the scenario is supposed to prove an SDK call or callback handler. Operations remain useful for
setup and inspection, but they cannot supply evidence for a boundary they bypass.

## Trace each boundary through logs

Correlation IDs are scoped to one boundary, not propagated through an entire scenario. A control
request that invokes an operation shares its ID with that operation's entries. A provider-shaped
request, each outbound delivery, each plugin log call, and a later `idle` control request have their
own IDs.

Read the latest structured entries for the same instance and, when known, service:

```sh
localhost_service_key="replace-with-configured-service-key"
localhost_instance_id="replace-with-instance-id"
pnpm exec localhost logs "$localhost_service_key" \
  --instance "$localhost_instance_id" --tail 50 --json
```

Use a known `correlationId` to group entries within its boundary. To move to the next boundary,
pivot using `instanceId`, `serviceKey`, `wallTime`, `virtualTime`, and provider-shaped resource or
event identifiers visible in the application and safe log attributes. Do not search for one
correlation ID end to end.

The runtime emits `request`, `operation`, `delivery`, and `plugin` entries. Read their `status`,
`message`, and safe `attributes` to distinguish work that may otherwise occur within the same
wall-clock second. `virtualTime` shows the instance clock when it is relevant; `wallTime` shows when
the entry was recorded.

Logs are a bounded diagnostic ring, not an audit trail. A non-zero `droppedEntries` means older or
oversized entries are unavailable, so reproduce the smallest failing scenario before drawing a
conclusion from absence. Body-like attributes are omitted and known sensitive values are redacted,
but still review entries before sharing them. If a request body is essential, capture only the
necessary fields at the application boundary with its own safe instrumentation.

## Treat asynchronous failures as evidence

Call `await instance.idle()` after the plugin schedules callbacks or other tracked work. If it
rejects, start with that control error's code, message, and correlation ID. The runtime does not emit
a task entry for the failure. Inspect nearby delivery and plugin evidence for the same instance,
service, and time instead of adding a delay. If `idle()` resolves, only plugin-tracked work is known
to be idle. Wait on the application's explicit completion boundary before asserting application
state.

Work scheduled for a later virtual time does not run merely because the current work became idle.
Advance the clock by a positive duration when the documented behavior depends on a later retry or
deadline, then wait for completion again. See [Virtual time and asynchronous work](/virtual-time)
for the distinction between clock movement, reconciliation, and idle work.

Some lifecycle failures require extra care. `LIFECYCLE_CONFLICT` is an umbrella for invalid
transitions, lifecycle timeouts, a closing or changing runtime generation, and time-reconciliation
conflicts. Read its message and inspect the current instance and clock state before choosing another
action. `INSTANCE_MUTATION_COMMITTED` means the mutation took effect but finalization did not finish
cleanly; do not blindly retry it. For a committed clock advance, the error details include the
`from`, `to`, `advanceId`, mode, and whether reconciliation remains pending. Read the current state
and those details before deciding whether any recovery action is needed.

Seed failures have action-specific recovery rules. [Seed test worlds](/seeding#recover-according-to-the-outer-mutation)
distinguishes an in-place seed failure from a failed seeded create or reset.

## Keep the broken boundary visible

During diagnosis:

- do not replace the application's SDK or HTTP call with a control operation;
- do not read or edit a plugin database from the application test;
- do not add a test-only success endpoint to the application or plugin;
- do not widen a cleanup command from one owned instance to project storage;
- do not label a provider difference a bug until the installed plugin claims that behavior.

If the plugin does not support the required request, response field, callback, or lifecycle behavior,
write down that precise compatibility gap. [Provider compatibility](/compatibility) explains the
evidence required for broader parity claims.

## Leave a useful diagnostic record

A report another person can act on includes:

- the localhost2137, plugin, SDK, and Node.js versions;
- the resolved config path, service key, and instance ID;
- the exact boundary exercised and the smallest reproducing command or application action;
- the error code and boundary-scoped correlation ID or IDs;
- the relevant structured log entries and `droppedEntries` count;
- `doctor` issue codes, expected behavior, and observed behavior;
- the plugin support-matrix entry or documentation claim when provider compatibility is involved.

Remove control tokens, provider credentials, personal data, and unnecessary request bodies. The aim
is a reproducible boundary failure, not a complete dump of the local environment.
